# Commits And Changelog

Use conventional commits so changelogs, release notes, and repo history can be generated rather than hand-curated from memory.

## Commit style

Use:

- `feat:` for user-visible capability.
- `fix:` for bug fixes.
- `docs:` for documentation-only changes.
- `ci:` for CI workflow changes.
- `test:` for tests.
- `refactor:` for code movement with no behaviour change.
- `chore(deps):` for dependency bumps.
- `chore(release): vX.Y.Z` for release commits created by `s/version++`.

Use a scope when it helps: `feat(cli):`, `fix(docs):`, `ci(release):`. Do not invent elaborate scopes that only make history harder to scan.

## Message body

Add a body when the reason is not obvious from the diff. Good bodies explain tradeoffs, migration notes, or why a surprising choice is deliberate. Do not restate the file list.

## Changelog

`CHANGELOG.md` is generated by git-cliff in Keep a Changelog shape. The release script regenerates it in the same commit as the version bump, before the tag is created.

The changelog should be useful to a user:

- Features and fixes matter.
- Routine dependency bumps usually do not, unless they fix a security issue or change supported platforms.
- Release commits themselves should be skipped by the changelog config.

[`koloki-co/dsc`](https://github.com/koloki-co/dsc/blob/main/cliff.toml) is the reference `cliff.toml` shape. Copy from a living repo rather than recreating a config from scratch.

## Release commits

Release commit format is exactly:

```text
chore(release): vX.Y.Z
```

Do not hand-edit a release commit after tagging. If something is wrong, fix forward with a new commit and release again as needed.

## Dependency commits

Dependabot PRs should land as `chore(deps): ...` unless the dependency update directly fixes a user-visible bug. Grouped routine minor/patch PRs are expected; high/critical security fixes can be reviewed and merged outside the weekly routine.

## Squash and merge

For ordinary feature PRs, squash or merge according to the repo's local preference. For release PRs in the CI auto-tag cascade, prefer merge commits so the `chore(release): vX.Y.Z` commit survives unchanged and git-cliff can skip it reliably.

## Delete merged branches

A merged branch has served its purpose. Left behind, branches accumulate until the graph no longer shows which work is live, and a stale branch invites someone to build on a base that has already moved.

- **Turn on "Automatically delete head branches"** in the repository settings, so the remote branch goes when the PR merges without anyone remembering to do it. `gh repo edit --delete-branch-on-merge` sets it; `gh repo view --json deleteBranchOnMerge` confirms it.
- **Merge with `gh pr merge --delete-branch`**, which removes the remote branch and the local checkout together.
- **Prune stale tracking refs** with `git fetch --prune`, or set `git config --global fetch.prune true` once. Deleting a branch on the remote does not remove another clone's tracking ref.
- **Confirm merged before deleting anything by hand.** `git branch --merged main` lists the safe ones, and `git merge-base --is-ancestor <branch> origin/main` answers it for a single branch. Prefer `git branch -d`, which refuses an unmerged branch, over `git branch -D`, which does not.
- **Leave other people's forks alone.** A contributor's fork appearing as a remote is not clutter to tidy: their branches are theirs, and the tracking refs cost nothing.

The end state to aim for is a repository whose branch list is `main` plus whatever is genuinely in flight.
